# Step 04 — First Dummy Producer

Parent: [PLAN.md](../PLAN.md)

## Goal

Create the second Spring Boot application — `payment-service` — and give Sentinel a place to receive raw signals from it. End the step with both services running locally and signals flowing over HTTP.

**Note on architecture:** producers emit `RawSignal` (loose, free-form). They do *not* classify events. Classification is the platform's job, added in [step 04.5](step-04.5-classifier.md). Producers are dumb on purpose — anything that can POST JSON should be a valid producer, regardless of language or shape.

## What to build

- Convert the repo to a **multi-module Maven build** (parent aggregator pom + child modules). This is where the split happens; earlier steps had a single-module `sentinel/`.
- New Maven module `payment-service/` — a Spring Boot app with:
  - A scheduled job that simulates payment authorizations every few seconds.
  - A simple internal "failure injector" — randomly fails N% of payments, with configurable rates per failure kind (provider timeout, declined, retry exhausted).
  - A `SignalEmitter` that POSTs `RawSignal` JSON to a configurable URL (Sentinel for now; sidecar later). Uses `RestClient`.
- Sentinel-side additions:
  - A new `POST /api/v1/signals` endpoint accepting `RawSignal` JSON.
  - Flyway migration `V2__create_raw_signals.sql` for the `raw_signals` table (separate from `incidents` and from the future `operational_events` table).
  - `RawSignalEntity`, `RawSignalRepository`, and a `SignalIngestService` that persists.
- No shared DTO jar between producer and Sentinel. Each side has its own class matching the wire JSON.

## The `RawSignal` shape (wire schema)

```json
{
  "id": "uuid",
  "source": "payment-service",
  "timestamp": "2026-07-17T12:34:56Z",
  "message": "stripe authorize timed out after 8s",
  "hints": {
    "level": "ERROR",
    "provider": "stripe",
    "durationMs": 8400
  }
}
```

Only `id`, `source`, `timestamp`, `message` are mandatory. `hints` is free-form JSON — a map of extra structured context the producer knows and wants to pass along. Sentinel stores it as `jsonb`.

## What to learn

- **Multi-module Maven layout** — parent aggregator pom (`packaging: pom`), child modules with slimmer poms, BOM-import strategy for version management, `spring-boot-maven-plugin` at child level.
- **Spring `@Scheduled`** for periodic work; **`RestClient`** for outbound HTTP.
- **Externalized configuration** — `application.yml` with environment-overridable URLs.
- **Wire-contract discipline** — the boundary between services is JSON, not shared Java classes. Producers and Sentinel each have their own `RawSignal` class; the JSON schema is what they agree on.

## Things to think about

- **Producer stays dumb.** Do not put failure-type strings in the producer's emitted signal (`type: PAYMENT_PROVIDER_TIMEOUT`). That's classifier territory. The producer says what happened in its own words (`message` + `hints`); the platform figures out the type.
- **Signal ID at producer.** UUIDs generated by the producer, not Sentinel. Critical for idempotency in [step 10](step-10-idempotency.md).
- **Hints are optional but helpful.** The classifier will match on hints when they're present. Producers should include what they naturally have — provider name, duration, HTTP status — but shouldn't fabricate structure to be helpful.
- **Storage separation.** `raw_signals` is an audit table. Once classifier lands (step 04.5), signals are also written to `operational_events`. Keeping the tables separate preserves the pre-classification truth even if rules change.

## Sub-steps

Break the work up like step 03:

- **04a** — Multi-module Maven conversion. Root parent pom, move Maven wrapper to root, slim `sentinel/pom.xml` to a child. `./mvnw clean verify` passes at root. No functional change.
- **04b** — Sentinel: `V2__create_raw_signals.sql`, `RawSignalEntity`, `RawSignalRepository`, `SignalIngestService`, `POST /api/v1/signals` endpoint. Test with a manual `curl`.
- **04c** — `payment-service` module: scaffold Spring Boot child, `@Scheduled` payment simulator, failure injector, `RestClient`-based `SignalEmitter` posting to Sentinel.
- **04d** — End-to-end integration test that runs both services (or mocks Sentinel with WireMock) and asserts a signal round-trips.

## Done when

- Both services start with `./mvnw -pl sentinel spring-boot:run` and `./mvnw -pl payment-service spring-boot:run`.
- Payment service logs simulated activity and successfully POSTs `RawSignal` JSON to Sentinel.
- Sentinel persists received signals to Postgres.
- An integration test exercises the flow end-to-end.

## Look ahead

The direct HTTP wiring here is replaced by sidecar → Kafka. But the `RawSignal` wire schema stays. Treat that JSON shape as a contract and try not to thrash it later. When rules and classifier come in (step 04.5), signals stop being terminal — they become the input to a pipeline.
